# The portable artifact is the harness around the skills, not the skills

What this repository contributes, and what should be carried to another project,
is the **harness**: the router, the workflow rules, the CI shape and the working
agreement that make the vendored skills productive. The skills themselves are
Matt Pocock's, unmodified, and already portable without our help.

This matters because the goal has been described as "the skills repo I will add
to other projects", and that framing points at the one layer that needs no work.

## The evidence

`.claude/skills` has been touched by exactly **one** commit — `a241d32`,
"vendor Matt Pocock's 22 promoted agent skills" — and nothing since.
`docs/agents/workflow.md` calls the directory vendored and hash-locked, and
although no lock file or CI check enforces that, the honour system held. Every
extension this repository made lives outside it.

So extracting "the skills" would produce a copy of upstream. The work is
elsewhere.

## Four layers, and only one of them is ours

| Layer                  | What it is                                                                                                                                           | Portable?                                                  |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **Skills**             | The 22 vendored skills                                                                                                                               | Already — it is upstream                                   |
| **Per-project config** | `domain.md`, `issue-tracker.md`, `triage-labels.md`                                                                                                  | Generated by `setup-matt-pocock-skills` from its own seeds |
| **Harness**            | `workflow.md`, `monorepo.md`, `content-types.md`, `ci-and-branch-protection.md`, `setup.md`, `AGENTS.md`, plus CI, hooks, Turbo and workspace config | **Ours, and homeless**                                     |
| **Domain content**     | `CONTEXT.md` and the ADRs                                                                                                                            | No, and should not be                                      |

The second layer is worth stating explicitly because it is easy to mistake for
ours: `setup-matt-pocock-skills` already carries seed templates and writes those
three files per repo. That problem is solved upstream, and re-solving it is the
obvious wrong turn.

## The contract between the two worlds is exactly three files

The boundary above is not a judgement call. It is observable, and it is narrower
than "everything in `docs/agents/`":

- **The generated files are still upstream's, verbatim.** `domain.md`,
  `issue-tracker.md` and `triage-labels.md` each differ from their seed template
  in the skill folder by **zero lines**. The installer ran and its output was
  never edited.
- **The skills read those three and nothing else.** Across all 22, the only
  `docs/agents/` paths referenced are `issue-tracker.md` (6 references),
  `triage-labels.md` (3) and `domain.md` (2). `workflow.md`, `monorepo.md`,
  `content-types.md`, `ci-and-branch-protection.md` and `setup.md` are referenced
  **zero** times. Upstream does not know those files exist.
- **The harness predates the skills.** `AGENTS.md` was added on 2026-06-23; the
  skills were vendored on 2026-07-25, a month later. The five bespoke
  `docs/agents/` files arrived on 2026-07-27, two days after vendoring, in this
  repository's own commits. None of it can have come from upstream.

So the seam is clean in both directions. Anything a skill needs, it takes from
those three generated files. **Everything else is ours to design freely, because
nothing upstream reads it** — the harness can be packaged, renamed or
restructured without forking a single line of Matt Pocock's work, and a new
project needs the skills, those three generated files, and whatever the harness
turns out to be.

That also sharpens what to watch. A future skill that starts reading a fourth
file would widen the contract, and widening it is the thing that would make the
harness hard to move.

## The harness splits again, and that is the real design question

Some of it is true of any repository running these skills:

- The rules in `workflow.md` — which skills are human-only, and why a
  hand-written issue loses the `blocked_by` edges that make a frontier computable
- The CI shape in `ci-and-branch-protection.md` — conditional per-workspace jobs
  plus one always-runs aggregate job as the single required check, because a
  skipped job blocks a merge rather than passing it
- The working agreement — draft pull request first, `/code-review` before it
  leaves draft, one concern per pull request, findings get their own commit
- `AGENTS.md` as a **router** rather than an encyclopedia, on the grounds that
  everything in it is paid for on every task

Some is true only of pnpm + Turborepo + Strapi + Next: `monorepo.md`,
`content-types.md`, and most of `setup.md`.

That split is the thing to get right before anything is extracted, and it is not
academic. The next destination — `strapi-next-monorepo-starter` — shares the
stack but runs **Node 24, pnpm 11.1.1 and Postgres** against this repository's
Node 22, pnpm 10 and SQLite. The generic half transfers unchanged. The
stack-specific half needs re-measuring, and
`0012-react-types-resolve-from-the-root.md` already says so about itself.

## Two findings that belong in the harness rather than in anyone's memory

**`/code-review` is expensive and worth it on code.** A run costs roughly 100k
tokens. In one day it disproved the central mechanism claim of a merged pull
request, and caught three real defects in another that lint, typecheck, tests and
build all passed — including a test that dodged the exact case it was named for.
The rule that follows is not "use it less" but "use it on code, skip it on
documentation, and do not treat the token cost as the deciding factor."

**Automated third-party review is a bonus, never a gate.** GitHub's Copilot
review produced findings on #57 through #61 and nothing at all on #62 or #63.
Anything that silently produces nothing cannot be relied on to catch anything.

## Consequences

"Add the skills to another project" is three steps, not one: vendor the upstream
skills, run `setup-matt-pocock-skills` to generate the per-project config, then
apply the harness — and only the third step is undocumented.

The harness has no home, no name and no install path. Giving it those is the next
piece of work, and the playbook is its documentation rather than a separate
deliverable.

This record does not decide how the harness is packaged — a repository, a
template, a skill that writes it, or prose someone follows. It decides only what
the thing is, so that the packaging question is asked about the right object.

## What would change the answer

Editing a vendored skill. The moment `.claude/skills` diverges from upstream,
there genuinely is a fork to maintain, and the shape of everything above changes.
`docs/agents/workflow.md` forbids it, nothing enforces that, and the enforcement
gap is now worth more than it was when the only cost was tidiness.
